# 共有キャンバス

256×256、整数座標の不透明丸ブラシ。ビルド・依存パッケージなし。白／ライトグレー／ダークグレーのUI、Material Symbols、拡大表示、IndexedDB、独立した描画順と更新番号、作者ごとのUndo／Redo、4秒間隔の差分取得と再送を実装。

## 公開先

https://uktea.github.io/shared-canvas/

`web/config.js` に共有GASの接続先を設定済み。以前に接続設定を保存したブラウザでは、その設定を優先する。

## ローカルで使う

Node.js 22以上とPython 3で `npm test`、`npm start`。http://localhost:8080 を開く。初期接続先は公開GAS。ローカル専用で使う場合は接続設定を空欄にする。HTTPSまたはlocalhostが必要。

## GAS・スプレッドシート

1. 新しいGoogleスプレッドシートを作成し、拡張機能 → Apps Scriptを開く。
2. `gas/Code.gs` と `gas/Core.gs` をそれぞれ同名ファイルに貼り付ける。プロジェクト設定でマニフェストを表示し、`gas/appsscript.json` を設定する。
3. スクリプトプロパティに `SPREADSHEET_ID` を設定する。値はスプレッドシートのURLの `/d/` と `/edit` の間。公開HTMLには秘密情報を置かない。
4. `setup` を実行して権限を許可する。CanvasのA1:IV256がRGB、A258:B258が反映済み更新番号。履歴はイベントログで、ストロークの有効状態はUndo／Redo履歴から再構築する。既存データがある場合は消さずに再構築する。
5. 「デプロイ → 新しいデプロイ → ウェブアプリ」。匿名共有を選ぶ場合は「自分として実行」「全員」を指定する。この選択によりURLを知る人が読み書きできる。Google Workspaceの管理設定により選べないことがある。
6. `/exec` URLを画面右上の接続設定に入力する。または `web/config.js` の `CANVAS_ENDPOINT` に設定する。`/dev` は使用しない。接続先ごとにローカルデータは独立する。ローカル専用で描いた内容の自動アップロードはしない。
7. GASコードを更新したら、新バージョンを既存デプロイに適用する。共通描画処理を変更した場合は `npm run sync-core` を実行して両方更新する。

### 既存GASを一括送信対応版へ更新する

1. Apps Scriptで `Code.gs` をこのリポジトリの `gas/Code.gs` に差し替えて保存する。今回 `Core.gs` とマニフェストの変更は不要。
2. デプロイ → デプロイを管理 → 既存ウェブアプリの編集 → バージョン「新バージョン」→ デプロイ。既存の `/exec` URLを維持する。`setup` の再実行は不要。
3. キャンバスを再読み込みする。GASの応答が `protocol: 2` なら最大50操作・256,000バイトの一括送信を使用する。未送信操作は従来のIDのまま再送する。

フロントだけを更新しても旧GASを利用できる。その間は1操作ずつ送り、一括送信とRGB更新の軽量化はGAS更新後に有効になる。

一括送信版の自動テスト23件で、送信上限による分割、通信中の操作追加、応答喪失後の再送、旧GASとの互換性、履歴の重複防止、範囲更新と全体再描画の一致を確認している。実GASでの速度は更新後の実測が必要。

## GitHub Pages

コードを対象リポジトリのmainブランチへ追加し、Settings → Pages → SourceをGitHub Actionsに設定する。同梱workflowが入口の `index.html` と `.nojekyll`、キャンバス本体の `web/` をまとめて公開する。トップURLは `web/` へ移動する。

mainブランチのルートを直接公開する設定でも、同じ入口からキャンバスを開ける。ルートの `.nojekyll` でREADMEのJekyll変換を無効化する。リポジトリが公開ならGASのソースも閲覧できるので、スクリプトプロパティや鍵をコミットしない。

## 実接続の受け入れ確認

2026-11-03確認：PagesはHTTP 200、直近の公開ワークフローは成功。GASは認証なしのGETでリダイレクト後にJSONを返し、`Access-Control-Allow-Origin: *` を確認。更新43のスナップショット（43イベント）の全65,536ピクセルが共通描画処理による再構築結果と一致し、差分取得も成功した。自動テスト11件成功。

実ブラウザでのCORS・POST・複数利用者の同時操作・処理時間・クォータは未検証。以下を受け入れ確認として実施する。

1. Pagesを開きGAS接続設定。NetworkでGETがリダイレクト後にJSONとして読めることを確認。認証画面のHTMLやCORSエラーなら公開設定を確認する。
2. 1点・斜線・端・太さ1/64を描く。POSTは `text/plain`、カスタムヘッダーなしで送信する。レスポンスを読めない `no-cors` は使わない。
3. CanvasシートのRGBと画面を確認する。初回取得時に共通描画処理による再構築結果と全65,536ピクセルを比較し、不一致はエラーにする。
4. 別ブラウザで同じURLを開き、同じ位置へ交互・同時に描く。AのUndoでBの描画が残り、RedoでAの元の重なり順が維持されることを確認する。
5. Aで2回Undo→Redo、新規描画→Redo不可、再読込後のUndoを確認する。
6. DevToolsのOfflineで描画→再読込→Online。未送信操作が一度だけ反映され、操作IDの重複行がないことを確認する。POST受付後に応答を遮断する場合も確認する。
7. GET/POST所要時間、GAS実行時間、同時操作数、履歴件数とリプレイ時間を記録する。運用規模はこの実測後に決める。

## 整合性と制限

* 座標は0〜255の整数ピクセル中心。Bresenhamで中心を補間し `dx²+dy² ≤ (太さ/2)²` の円盤を塗る。ブラウザのアンチエイリアスは使用しない。太さはこの円盤のパラメータなので、偶数幅でも被覆幅が奇数になる場合がある。
* ストロークは最大2,000点で確定する。1セルのJSONが過大にならないための入力上限。上限到達後はポインターを離して次のストロークを描く。
* LockServiceで読み取りと書き込みを直列化する。履歴を先に確定しRGBを書き、flush後に反映済み番号を書く。途中失敗なら次回要求で履歴から修復する。手作業でCanvasや履歴のセルを変更しない。
* 通常の配信は差分。500操作以上の差分や番号不整合ならスナップショットを再取得する。初期版は全履歴を保持する。Undoを正しく扱うため初回取得はRGBと全イベントを含む。
* 未送信操作を200msまとめ、最大50操作・256,000バイトずつ送る。通信中に増えた操作も次の一括送信へ取り込む。初回同期後は送信前のGETを省き、POSTの応答から他の作者の差分も取得する。旧GASでは1操作ずつの送信に戻す。
* GASは一括送信の全操作を先に検証し、操作ごとのID・更新番号・描画順を保つ。履歴の書き込みとRGBの反映は一括送信につき各1回。RGBは追加・Undo・Redoの対象ストロークを囲む矩形だけ更新する。範囲が広い場合は全65,536セルになる。中断からの修復と `setup` は全体を再構築する。
* 通常の差分取得は不足分の履歴行だけを読み、RGBや全履歴を読み直さない。書き込み時の検証・再描画は引き続き全履歴を読む。履歴増加や多数利用時の性能は保証しない。ベース統合は未実装。
* 作者IDはブラウザ内の識別子で、本人認証ではない。サーバーは他の作者IDへのUndoを拒否するが、作者IDのなりすまし防止には未確定の認証方式を追加する必要がある。認証が必要な運用のまま匿名公開しない。
* 同一ブラウザの複数タブによる同時編集は未対応。1接続先につき1タブで使う。ブラウザ間では別の作者として動作する。IndexedDBを消去すると作者・Undo履歴・未送信分は失われる。
* 無効な操作や同一作者の競合は未送信のままエラーを表示する。サーバーが受理したことを確認できるまで操作を削除しない。
